# MetaLearn scoped billing integration (v1)

This independent New API service retains its upstream identity and AGPL license. The integration is a product-owned seam; request pre-consumption, settlement and pre-consumption refund stay upstream-owned.

All routes are under `/api/metalearn/billing`, authenticated by `Authorization: Bearer <METALEARN_BILLING_INTEGRATION_TOKEN>`. Missing/empty configured token disables the routes (401). The token does not authorize any administrator API. Requests and responses containing tokens must never be logged. JSON response envelope: `{"success":true,"data":...}`; errors: `{"success":false,"code":"..."}` with fixed codes.

- `POST /users`: `{business_user_id: string}` (canonical, non-nil UUID). HTTP 200 data `{business_user_id, gateway_user_id: int, relay_token: string}`. Idempotent dedicated user/token, initial wallet quota zero, no registration or invitation reward, billing preference `subscription_only`. Relay token returned only to trusted server. An inactive/deleted mapping or mismatched dedicated token is rejected instead of recreated.
- `POST /periods`: `{business_user_id, channel: string, period_key: string, plan_id: int, start_time: int64, end_time: int64}`. Times are UTC Unix seconds (not milliseconds), exact paid bounds with `end_time > start_time > 0`. `channel` lowercase ASCII `[a-z0-9_-]`, 1–32 chars; `period_key` non-whitespace printable ASCII, 1–128 chars. User must already be provisioned. The unique key is `(channel,period_key)`. Same immutable tuple returns the same result; differing identity, plan or times returns 409. Total quota comes only from the enabled server-side `SubscriptionPlan.TotalAmount` snapshot (>0), never request quota. A dedicated `UserSubscription` stores exact start/end and `source=metalearn`, no group upgrade and no intra-period reset. No changes to global plan settings. A revoked key always returns 409 on grant, including refund-before-grant tombstones.
- `POST /periods/revoke`: same DTO. HTTP 200, including repeated revoke. Tombstone is recorded even if provisioning/grant has not arrived; no free quota is created. Existing subscription becomes cancelled without changing its paid bounds or resetting used quota. Immutable tuple conflicts return 409. This is a refund/revocation operation; cancellation of auto-renewal alone must not call it.
- `GET /users/:business_user_id/subscriptions`: HTTP 200 data `{business_user_id, gateway_user_id, subscriptions: [...]}`. No relay/admin credentials. Returns exact known paid periods, including revoked/future/expired periods. User missing =>404.

Every period result (including query items) and subscriptions query data also declares `quota_per_credit: 1000`. This declares the integration unit (milliCredits), not evidence that upstream model pricing ratios are already configured; do not enable monthly billing until native price/ratio equivalence is verified.

Period result and query item: `{business_user_id, channel, period_key, plan_id, start_time, end_time, status: "granted"|"revoked", subscription_id: int, amount_total: int64, amount_used: int64, amount_remaining: int64}`. Revocation before grant has subscription_id and quota values zero. These are native New API integer quota units; no Credits conversion is performed by this seam. Backend plan bindings/conversion are separately configured and verified; clients cannot choose quota or conversion. `status=granted` records grant state, not a promise that a future/expired period is currently spendable. Active queries and funding selection require `start_time <= DB-now < end_time`.

Fixed errors: 400 `invalid_request`; 401 `integration_unauthorized`; 404 `user_not_found` or `plan_not_found`; 409 `identity_conflict`, `period_conflict`, `period_revoked`, `plan_not_eligible`; 503 `integration_unavailable`. No database errors or credentials appear in error bodies.

## Implementation and verification boundary

Reference fork: `https://github.com/xland242643/new-api.git` at `77fac055722165fd088e85e3173d7de68f015d0a`, complete history, detached read-only vendor copy. Changes live in the same-Git `app-server/services/new-api` worktree on `codex/metalearn-billing-periods`. Existing attribution, license, module identity and administrator APIs remain upstream-owned.

Product seam: `model/metalearn_billing.go`, `middleware/metalearn_billing_auth.go`, `controller/metalearn_billing.go`, `router/metalearn_billing.go`. Dedicated users and relay tokens use group `metalearn-monthly`; token-level unlimited quota removes a redundant token budget, while user billing remains `subscription_only` with zero initial wallet quota. The relay token carries no administrator role. Requests are at most 4096 bytes and unknown fields are rejected. The scoped credential is accepted only by this route group. ORM failure logging is silenced for this seam to prevent relay keys appearing in failed INSERT SQL.

Database uniqueness + transaction row locking coordinate multiple service processes. A period row stores the immutable request tuple, grant/revocation state and subscription link. Revoke preserves paid bounds and consumption counters. A refund-before-grant tombstone does not depend on a user or plan already existing. The grant snapshots `SubscriptionPlan.TotalAmount`; `source=metalearn` prevents future plan edits from resetting paid quota. Shared plans are not modified. Queries return exact stored periods; `amount_remaining` is the unused native quota snapshot, and spendability also requires granted state and current paid bounds.

Observed upstream defects and narrow corrections in `model/subscription.go`:

- `GetAllActiveUserSubscriptions`, `HasActiveUserSubscription` and `PreConsumeUserSubscription` omitted start-time eligibility; funding can therefore select a future paid period. They now require `start_time <= DB-now < end_time`. Active upgraded-group checks use the same eligibility condition.
- `RefundSubscriptionPreConsume` opened a transaction then called `PostConsumeUserSubscriptionDelta`, which opened another transaction on global DB. `TestMetaLearnNativeRefundAtomic` reproduced the deadlock on single-connection SQLite (5-second timeout; stack waits on the nested BeginTx). Quota delta is now performed through a private helper on the original transaction; arithmetic and quota limits are unchanged. The refund marker and quota rollback together if either write fails. Funding/preconsume/refund row locks use GORM `clause.Locking` rather than the obsolete query option; unrelated payment/admin locking code is unchanged.
- Preconsume request-ID replay rejects another user instead of returning a foreign reservation. Server request-ID generation is unchanged.

Tests run without payment, model requests or cloud billing: race-enabled `go test -race ./model ./router -run ^TestMetaLearn` passed; full `go test ./model ./router ./middleware` passed; MetaLearn-focused concurrency uses file SQLite WAL with up to eight connections. Dedicated tests cover concurrent repeated provisioning/grants, wrong business identity/plan/time conflicts, no free reward, future eligibility, plan-edit immutability, revoke-before-grant, grant/revoke race, repeated revoke, missing/disabled credential, unknown quota/group fields, secret-free queries, same-transaction refund, rollback after marker-write failure, native reserve/settlement/refund. PostgreSQL/MySQL migration/concurrency have not been exercised on live engines in this environment; GORM abstractions and unique indices retain upstream three-database compatibility. There is no local Docker/psql executable.

## Pricing evidence (read-only, activation still pending)

`common/constants.go` declares `QuotaPerUnit=500000`. `pkg/billingexpr/settle.go::quotaConversion/ComputeTieredQuotaWithRequest` uses `exprOutput / 1000000 * QuotaPerUnit * GroupRatio`; `relay/helper/price.go` freezes the same conversion for preconsume. Therefore, if model coefficients are correct USD standard prices and a fixed billing exchange rate is `FX` CNY/USD, setting the monthly group's effective ratio to `FX * 0.2` yields `100000` quota per CNY = 100 Credits per CNY at 1000 quota per Credit. This is a derivation, not a production price verification.

`service/text_quota.go` prices ordinary input, cache reads, cache writes and output separately in ratio mode; `service/tiered_settle.go::BuildTieredTokenParams` and the billing expression engine support cache read/write, output and context tiers. `len` retains full input context, while separately priced cache categories are excluded from `p`; tier boundaries must use `len`. Long-context pricing requires explicit `billing_setting.billing_mode=tiered_expr` and a verified per-model expression; the default settings are empty and ratio mode alone does not create context tiers. `relay/helper/price.go::HandleGroupRatio` gives `GroupGroupRatio` precedence over a group's ratio; `OtherRatios` and request multipliers can also change cost. Static default model rates and `USD2RMB=7.3` are not evidence of current provider prices. All supported model/rate/tier/cache branches need verified fixtures before monthly billing activation. This extension changes no pricing configuration and enables no feature flag.

## Settlement receipt gap

An existing consume log is not an authoritative settlement receipt: `service/text_quota.go` records its calculated quota even when `SettleBilling` returns an error. `service/log_info_generate.go::appendBillingInfo` includes preconsume/postdelta and subscription identity but no durable settled flag. No receipt API is added here; downstream must keep `awaiting_gateway_receipt` rather than report intended `Log.Quota` as a successfully settled fee or infer a single request's charge from concurrent balance changes. Native amount calculation, settlement core and request-ID generation are retained.
